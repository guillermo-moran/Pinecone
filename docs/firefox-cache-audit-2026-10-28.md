## Prioritized Findings

### 1. P1 Correctness: Decode Publication Can Certify Bytes From an Older Epoch

**Source-inferred risk, not a reproduced Firefox failure.** [BlockCache:1160](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:1160) fetches/decode-copies instructions incrementally. [BlockCache:1340](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:1340) then stamps the entry with the *current* local code, shared code and translation epochs. Only afterward does [BlockCache:820](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:820) register pages and capture their generations. There is no encompassing before/after validation tying the decoded bytes and mappings to these certificates.

A concrete adversarial sequence is a block crossing a 4 KiB boundary: fetch the first page at epoch E; publish a peer TLBI remapping that page; fetching the second page synchronizes the TLBI at [GuestMemory:2416](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:2416), advancing the local decoded-mapping epoch; install the entire block certified for E+1. The first page's old PA/instructions can now pass the equal-epoch fast path. A completed code write between reading a word and capturing its generation can similarly associate old bytes with the new generation. On a first-ever code page, registration itself is late, so just comparing a global code epoch before/after is insufficient if a concurrent writer did not yet regard that page as code.

**Action:** make decode publication use a stable mapping/content snapshot protocol, including code-page registration ordering. Reject/retry when a relevant epoch/generation changes during acquisition; do not simply stamp whatever epoch is latest. The existing validation callback epoch recheck at [BlockCache:542](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:542) protects revalidation, not initial construction. Also review the direct-fetch `memcpy` at [BlockCache:1173](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:1173), versus the atomic fetch at [GuestMemory:2597](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:2597); atomic word reads alone would not solve snapshot certification.

**Required coverage:** deterministic interleaving after first-page fetch and before publication, both remap and same-PA code replacement; first-ever executable-page registration; the second virtual page aliasing the first physical page; execute permission revoked on either page. Verify architectural results and fault PC, not merely cache counters. These cases should accompany longer continuation because stale decoded tails become more consequential.

### 2. P1 Performance: Scoped TLB Invalidation Becomes Global Decoded-Mapping Revalidation

**Measured:** validation and mapping-translation stack costs above. **Established mechanism:** [BlockCache:516](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:516) checks shared page generations when the shared code epoch differs; returns immediately when the local code epoch matches; otherwise retranslates once per virtual code page if its translation epoch differs. A successful retranslation preserves the decoded entry/program. It does not normally decode again on every TLBI.

However, [GuestMemory:1699](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:1699) applies a scoped TLBI to the TLB and then unconditionally dirties decoded mappings globally. [GuestMemory:1744](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:1744) does the same once per consumed shared journal batch. [BlockCache:1099](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:1099) clears the decode window and advances both `translation_epoch` and `code_mutation_epoch`, despite unchanged physical bytes. Thus a data-only or unrelated-ASID invalidation can require every subsequently visited code block to revalidate its executable mappings.

The indexed TLB already has finer ASID/VA/global/leaf-extent stamps at [GuestMemory:1637](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:1637). Decoded mapping certificates discard that selectivity. On an epoch change, a superblock also validates each distinct constituent block at [Native:14074](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizNative.c:14074); different blocks on one virtual page still cause repeated mapping checks. Deduplication is by block identity, not executable mapping.

**Action:** retain executable-mapping certificates at page/context granularity and make their invalidation as scoped as the existing TLBI metadata. Multiple blocks can reuse a valid page certificate, while physical code generations remain separate. Do not make decoded validity depend on an instruction-TLB slot staying resident: decoded entries survive TLB eviction, already explicitly tested. Keep conservative full invalidation for geometry changes, unsupported TLBI forms, journal overflow and wrap.

**Inference limit:** the samples prove retranslation is hot, not that unrelated TLBI is its dominant trigger. Instrument cause-specific decoded-epoch increments before claiming an ASID/TLBI speedup. Safe RAM continuation reduces invocation/checkpoint frequency but does not fix this global certificate invalidation; reducing both is complementary.

### 3. P2 Performance: Context Retention Exists, but Context Switches Still Dirty Every Certificate

[BlockCache:290](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:290) canonicalizes keys: retain the selected address-half's TTBR base, discard ASID bits and the opposite TTBR, and retain SCTLR/TCR/current EL. This already allows high-half kernel code reuse across low-half address-space switches. It is incorrect to describe this implementation as flushing all decoded code on every TTBR write.

The full stage-1 state comparison at [GuestMemory:1754](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:1754) includes both TTBRs, their ASIDs and EL. Any difference through [GuestMemory:3781](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:3781) dirties all decoded mapping certificates; only geometry changes clear the indexed TLB. ASID changes clear hot copies at [GuestMemory:1806](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:1806). Native exception transitions use a separate EL setter at [GuestMemory:3924](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:3924), so do not count every SVC/ERET as a full epoch bump without measuring the actual path.

**Action:** distinguish switching to an already-known context from invalidating that context's mappings. Reuse context/page certificates where their own invalidation stamps remain valid. Preserve current EL, permissions, selected root and effective ASID in the certification logic even though decoded-byte keys are canonicalized. Effective ASID selection depends on TCR.A1 and 8/16-bit mode ([GuestMemory:1782](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:1782)). Merely deleting the current epoch bump would be unsafe: two ASIDs can have different cached non-global translations for the same root/VA. Same PA is also insufficient after PXN/UXN/permission changes.

**Required coverage:** same-root/different-ASID mappings; A1 selecting ASID from the opposite TTBR; 8/16-bit ASID modes; global versus non-global entries; ASID reuse; EL0/EL1; low-half root changes retaining valid kernel code; unchanged PA with revoked execute permission. Require both correct output and no additional mapping-validator calls for genuinely unrelated changes.

### 4. P2 Performance: Successor Selection and Threaded Preparation Repeat Validation

**Measured:** successor lookup accounts for 3.8%/9.7% of run stacks, including 240/844 validator stacks. **Source:** [BlockCache:1711](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:1711) validates the source, then [BlockCache:1721](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:1721) validates both candidate targets *before* comparing their keys at line 1724. An untaken or foreign-context successor can therefore invoke translation unnecessarily. An exact-key hit still scans the second slot.

[Native:14793](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizNative.c:14793) checks the predecessor before recording a link; [BlockCache:1784](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:1784) rechecks source and target, then may validate existing candidates to choose a replacement. The separate direct-link cache already has an epoch fast path at [Native:13259](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizNative.c:13259).

On the threaded path, [Native:14832](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizNative.c:14832) prepares the program to decide eligibility; execution calls prepare again at [Native:13754](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizNative.c:13754). Both enter the code-current validator at [BlockCache:1517](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:1517), even before the negative-eligibility check. The checkpoint branches currently restart selection at [Native:14877](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizNative.c:14877) and [Native:14903](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizNative.c:14903).

**Action:** first validate candidate identity/serial, then compare its key, then validate mappings only for matching candidates. Preserve recent-successor selection semantics. Share a selection-scoped, pinned program/validation result between eligibility and execution, guarded by reset, serial, local/shared code and relevant mapping epochs. Reuse existing execution-span safeguards ([Native:14136](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizNative.c:14136)); do not cache a naked program pointer across callbacks. Epoch-match checks are cheap individually but recur at the measured short invocation length. Removing duplicate calls alone does not remove the first retranslation after an epoch transition.

**Required coverage:** nonmatching/unmapped successor must not invoke the mapping validator or deliver a speculative guest fault; matching successor still validates; replacement slot with identical address but new serial; two conditional targets and recent-successor behavior; self-links; checkpoint invalidation between selection and use; peer code write between the two preparation sites. No later stage may acknowledge an epoch newer than the one it validated.

### 5. P2 Performance: Threaded FIFO Churn Re-Decodes Existing Instructions

The decoded cache has 32,768 entries ([BlockCache:21](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:21)), but only 256 owned threaded programs ([BlockCache:169](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:169)). Hits do not refresh replacement order at [BlockCache:1526](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:1526): this is deliberately FIFO despite the `threaded_lru` name. Eligibility/negative/OOM results already live on decoded entries and survive auxiliary-program eviction. Recommending negative caching as a new feature would miss existing behavior.

On a program miss, [BlockCache:1551](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:1551) extracts raw words from decoded instructions. [ThreadedPrototype:385](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizThreadedPrototype.c:385) allocates operations, and line 399 decodes those words again. The measured 75/260 decoder stacks under creation identify redundant decoding independently of whether the miss was capacity, cold admission, code invalidation or a recycled entry.

**Action:** add an internal constructor consuming the already-decoded immutable instruction array, preserving the public raw-word constructor and all raw-word/reserved-encoding eligibility checks. Coordinate program ownership with the continuation owner; operations contain internal pointers and cannot simply be shallow-copied to another allocation. Separately measure FIFO recreation before selecting a retention policy or larger byte budget. A one-hit browser instruction stream can churn FIFO, but this run does not quantify the working set or prove capacity is the cause of every creation.

**Synergy:** memory exits force restart at an interior PC and clear predecessor identity ([Native:15064](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizNative.c:15064)); interior PCs are different decoded-cache keys. Safe continuation avoids some suffix lookups/decodes/program admissions and executes more of each constructed program. That amplification is source-inferred, not separately counted in these metrics. Measure creation/retired-instruction ratios again after continuation before growing the pool.

**Required coverage:** raw-word and decoded-input constructors produce identical CPU/memory/status results; reserved encodings and unsupported suffixes remain rejected; all branch targets/internal pointers stay valid; >256 admissions while a program is executing; clear, eviction and OOM with a live pin; feature toggling and negative eligibility. Keep bounded resident plus retired-program memory, not just 256 resident owners.

### 6. P2 Measurement: Current Counters Cannot Assign the Churn, and Scoped Miss Labels Mislead

The supplied JSON exports prototype boundaries but no decoded-cache statistics, creation/destruction counts, validator causes or TLB walks. Threaded cache diagnostics are compile-time opt-in at [BlockCache:11](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:11); detailed memory counters are runtime-gated at [GuestMemory:102](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:102). Existing source support is not evidence these counters were collected.

Additionally, a scoped invalidation makes `avz_native_fast_revalidate_tlb_entry` clear `valid` ([GuestMemory:1652](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:1652)). The instruction miss classifier at [GuestMemory:2466](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:2466) recognizes invalidation only from a still-valid entry with a mismatched global generation; the scoped-invalidated slot is now `first_invalid`, so the miss is classified as cold. This is a diagnostics defect, not evidence that the translation itself is incorrect.

**Action:** collect per-vCPU interval deltas with explicit reasons: mapping-epoch bump (ASID/root/EL/geometry/local TLBI/shared batch), validator fast/slow/failure/epoch-race paths, instruction hot/set/walk outcomes, decoded cold/eviction/stale misses, suffix-PC admissions, program creation/recreation/retirement and prefetch use/waste. Preserve the scoped rejection reason before clearing an entry. Separate mapping-validation translation from demand fetch in counters. Export these through the existing snapshot rather than printing per dispatch. Do not use the cumulative boot milestone fields as Firefox startup timing.

Decode window reuse and adaptive same-page prefetch already exist ([BlockCache:1136](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:1136), [BlockCache:1356](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizBlockCache.c:1356)). There is no measured basis here to enlarge the decoded cache, disable prefetch globally, or rewrite the decoder.

## Epoch and Lifetime Guardrails for Continuation

- `mutation_epoch`/entry serial track retirement/replacement; `reset_epoch` tracks cache reset. Neither is interchangeable with code bytes or executable mapping validity. A pinned allocation can remain alive while its code is invalid.
- Local `code_mutation_epoch` combines physical-code generation changes with mapping invalidations. `translation_epoch` distinguishes when instruction translation is necessary. Shared `code_mutation_epoch` causes per-physical-page checks; shared `translation_epoch` is a separate TLBI journal signal. Checking only shared code misses remaps with unchanged bytes.
- Ordinary data writes do not universally invalidate code. [GuestMemory:1539](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:1539) gates shared code generation changes on tracked code pages. The global code bitmap is sticky ([GuestMemory:942](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:942)); a formerly executable physical page reused for data can still dirty the global code epoch. Its contribution here is unknown. Do not clear these bits using one vCPU's local refcount: another cache, trace or pinned program can still depend on the page.
- Keep the native shootdown boundary at [GuestMemory:3895](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemory.c:3895). Memory hot helpers reject a pending shared translation epoch ([GuestMemoryInternal:191](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizGuestMemoryInternal.h:191)); a register-only tail also needs a bounded observation point. The existing runner bounds one invocation to at most one block's instruction count (maximum 16), including backward branches ([Native:13759](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizNative.c:13759)). Removing checkpoints is not permission to turn that into an unbounded loop.
- A successful generic memory helper is not a direct-RAM safety certificate: it can have invoked MMIO/host code, synchronized a remap, changed code, or released the program. Current `TP_MEMORY` intentionally captures metadata before the helper and never dereferences the program afterward ([ThreadedPrototype:213](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizThreadedPrototype.c:213)). Preserve this behavior on slow/fault paths and use the owner's explicit safe-continuation contract for RAM.
- Timer/IRQ accounting, host preemption and exact fault retirement are independent of cache validity. Successful store completion must not retry after a side effect; faulting loads/stores must publish the retired prefix without executing the tail. Check all budgets, including a memory instruction exactly exhausting the budget; the old adapter forces such outcomes back to revalidation at [Native:13766](/Users/gmoran/Documents/Projects/arm64viz/Sources/ARM64VizNative/ARM64VizNative.c:13766).
